A mental health app that works completely offline with no AI involved. Where a phone can run one, a small model improves the wording — it is never required.

The rule everything follows from

  • AI may make a response fit better. It may never be needed for one, and it may never come between someone and a crisis helpline.

How it is built

Four layers. The bottom one is the product; everything above it is a bonus that can fail silently.

answering a check-in — each layer used only if the one below allows it
Level 3 CloudOptional, off by default, never for anything sensitive. opt-in
Level 2 Language model, on the phoneRewrites approved wording to fit the moment. It cannot invent its own. if device allows
Level 1 Understanding, on the phoneReads tone and picks which prepared response fits best. if device allows
Level 0 Human-written answersA curated bank of responses, chosen by fixed rules. No AI whatsoever. always runs
Safety sits beside all four, not inside them. Crisis wording is fixed, human-written and never touched by a model — whichever layers happen to be running.
Show the architecture

Every check-in follows the same path. The safety check runs first and cannot be skipped, and both routes end in one shared response format — so the screens never need to know which route was taken.

If risk is found: fixed, human-written wording and the helpline. Nothing is generated, reworded or re-ranked.

Otherwise: rules pick a response from the curated bank. This alone is a complete answer.

The on-device model may improve the wording. Its output is checked against the schema and accepted whole or thrown away whole — never patched.

Both routes produce the same shape, so the interface renders one thing and cannot leak which path ran.

Consent sits between the phone and the network. Everything up to the on-device model runs with no network and no permission needed. Nothing crosses to a server without explicit, separate consent.

The rules that keep this true are held by CLEAR, the five-layer system I designed on this project.

Behind the scenes
  • The model never writes. It is handed a set of approved sentences and may only choose and join them. A guard between the model and the screen rejects anything not on that list — so “the AI said something wrong” is not a failure this app can have.
  • What it remembers are categories, not words. It records that someone tends to prefer short, low-effort suggestions at night — never the sentence they typed. That memory fades, so a bad week cannot define someone permanently.
  • The classifier may say “I don’t know”. Reading emotion from text is unreliable, so it declines rather than guesses and the app asks instead. Accuracy comes from knowing when to abstain.
  • Everything in the app varies to avoid repeating itself — except the crisis wording. That stays a fixed set of five human-written responses. Adding variety there would mean showing someone words nobody had reviewed, at the worst possible moment.
  • Most mental-health apps break when the network does. Moorwell answers fully at the base level, so a weak signal, an old phone or a failed model changes nothing the user can see.

How correctness is held

  • Its safety rules are assertions that fail the build, not documentation — listed below.

Run, watch and answer coding agents on your own computer, from your phone.

How it is built

Your machine does the work. The phone is a window onto it, and the relay in the middle is deliberately kept ignorant.

what you hold
Phone

Watch what each agent is doing and answer the ones that are blocked. Holds no logic of its own — it only draws what the engine gives it.

what carries it
Relay

Passes messages between the two. Everything through it is sealed, so it can deliver your work without being able to read it.

what does the work
Your computer

Runs the coding agents, using the tools and subscriptions you already pay for. Nothing moves to someone else’s cloud.

The engine is written once, in Rust, and shared with the phone app — so a Mac, iPhone or web version later costs a binding rather than a rewrite.
Show the architecture

Tether is built on five named layers, and one commitment underneath them: the event log is the only truth — everything else can be deleted and rebuilt from it.

SCALEfive layers, one rule
Surface

The per-device shell — Android today, desktop and web later. Each one declares what it is capable of, and is given nothing it cannot handle.

thin
Core

Portable Rust: the protocol, encryption, git, the event log, the offline queue. A test forbids it from importing anything device-specific.

shared
Atlas

The project’s own knowledge, ranked by how expensive it is to consult, so the cheap answer is found first.

tiered
Ledger

An append-only encrypted log of everything that happened. Every entry is stamped with device, session, agent and order.

the truth
Enforcement

Rules and the checks that hold them, kept together — because a rule nothing checks is just prose.

tested
Why this pays off. Crash recovery, moving a session between devices, seeing every machine at once and catching up after being offline are not five features to build. They all fall out of keeping one honest log.

SCALE’s Atlas and Enforcement layers are CLEAR carried over from Moorwell — the same method, a different language.

Behind the scenes

What the relay is actually allowed to see. Each sealed message carries exactly seven fields and nothing else:

sessiondevicesequencemachineagentnonceciphertext
  • No folder names, no repository names, no file paths — and no timestamps beyond what the network itself needs. The one readable field is which agent program is running, and it is on the wire only because a blind relay cannot route without it. That trade-off is written down rather than glossed over.
  • Nothing is overwritten. Every change is appended to a log, and the current state is worked out by replaying it — so a phone that was offline catches up exactly instead of guessing, and a crash resumes where it stopped.
  • The contract lives in shared test files, not in either language. Rust and Kotlin both read the same fixtures, so the two halves cannot drift apart while each looks correct on its own. They did exactly that once, which is why the rule exists.

How correctness is held

  • The test suite is itself tested: the build deliberately breaks the code and fails if the tests do not notice.

Share a reel, video, link, PDF or voice note and get a typed, editable note — then ask across everything you have saved, with answers that cite the note they came from.

How it is built

The phone owns your notes. The server only does what costs money, and the AI behind it can be swapped without shipping an update.

what you hold
Phone

Every note lives in an encrypted database on the device and works with the network off. Plain notes stay plain — AI runs only when asked, with Keep or Undo.

what holds the keys
Gateway

A thin Python service and the only thing holding vendor keys. It turns a shared link or file into a structured note, and meters what each one costs.

what can change
AI providers

Every AI step sits behind its own layer. Which provider and model it uses is server configuration, switched remotely, never a code change.

The ledger is the only truth. Every change is an append-only event, and every screen is a projection of that log — the same idea as Tether, carried into a different product.
Behind the scenes
  • The model never rewrites your words. When it tidies a note it returns the numbers of the pieces to keep and in what order; the server writes every item from the original. Checking a model’s rewrites kept missing cases, so the design removed the chance to do harm.
  • Three levels of privacy. Standard sync; an app lock with an encrypted on-phone database; and opt-in end-to-end locked notes, with secret fields inside them. Every feature works on ordinary notes.
  • Every feature has a server-side switch. Any module can be turned off remotely without touching data, and a short list — notes, locked notes, account, backup — can never be switched off.
  • One bad item never stops the rest. An unreadable row is quarantined rather than fatal, and one malformed server event cannot stall sync for everything behind it.
  • Nothing is hard-coded twice. Strings, numbers, motion, icons and shared widgets each live in one place, held by build gates that fail if a new one slips in outside it.

How correctness is held

  • Every hard rule is a gate the build runs, so a rule cannot quietly stop being true.

Design

Design systems

I specify the product as well as build it. Moorwell is on its second design system, written in full before implementation began. It is a re-layer rather than a reskin: every feature is kept, while layout, hierarchy, typography, colour and motion are rebuilt. Four decisions govern it.

Structural

  • Additive by construction. Every surface is the same three parts: panel, label row, optional drawer. A new feature becomes a row inside an existing group, never a new card. The home screen does not lengthen as the product grows.
  • Progressive disclosure. Secondary depth resides in in-place drawers rather than additional screens.

Expressive

  • Theme as configuration. Four palettes and a night mode are driven by a single token set; adding a fifth is a data entry, not a redesign.
  • Restrained motion. Entry and open transitions only. Nothing loops, drifts, or fills in the manner of a progress indicator — the latter is prohibited by the product's own rule against displaying what remains.

Colour carries mood, not status. Softness reads as safety. Motion should be biological, not mechanical.

Three of the eleven principles the design system is specified against

The mascot is rendered in code, not shipped as artwork. It has to morph across five moods and five palettes, so it is a CustomPainter taking size, mood and theme. All geometry is a fraction of its size, so one implementation serves both the 46-pixel and the 170-pixel instance. Artwork would have meant twenty-five exported files and a redraw on every palette change.

The specification covers design psychology, every screen, the mascot, an illustration set and a working prototype — built across 19 files.

Practice

How I keep code correct

The same habit runs through client work and my own: a rule that nothing enforces is a rule that will quietly stop being true, so I put correctness in the build rather than in a convention.

In client work

  • Al Tazaj — role-based menu visibility verified across all four flag states, so employee-only items cannot reach a public menu through an untested combination.
  • Global Neuro & Spine Care — over-the-air update capability, so a defect found in production is not held hostage by a store review queue.
  • Penda — framework migrations and breaking dependency upgrades across a shipped portfolio with no production regression.

In my own projects

  • Tether — the test suite is itself tested: the build deliberately breaks the code and fails if the tests do not notice.
  • Moorwell — the clearest example, because the stakes are highest. Its safety requirements are not documentation; they are assertions that fail the build.

The method — used on Moorwell and Tether

Rules have to survive the person who wrote them. I keep five layers, each a real file rather than a concept. I designed this on Moorwell (Flutter), then carried it into Tether (Rust and Kotlin), where it became SCALE’s Atlas and Enforcement layers.

CLEARfive layers, kept separate on purpose
C
Continuity — what is happening now, and what a previous session left unfinished.CONTEXT.md
L
Law — the rules, in one file, each marked with whether a test enforces it or nothing does.AGENTS.md
E
Enforcement — every rule that can be checked, written as a test that fails.test/
A
Atlas — why each decision was made, and what the evidence was.docs/
R
Record — what is true today, and an append-only history of how it got there.STATUS.md

The value is the loop between them. An incident is written down in full, including the embarrassing part, then distilled into a one-line rule, and that rule becomes a test that fails. A mistake is only finished when it cannot happen again quietly. Four of the five layers are plain markdown — only Enforcement needs a toolchain, and only a test suite in CI.

What the layers hold in practice

  • A catalogue of failure modes — each one a real incident from the repository, paired with the specific check that would have caught it.
  • An onboarding budget enforced by test: documentation carries a word cap derived from the existing corpus, because instructions nobody finishes are instructions nobody follows.

Recovering from interruption

  • Every file write is checkpointed to a private git reference, so work interrupted mid-task is recoverable without polluting the project history.
  • Concurrency rules learned the hard way — git worktrees isolate the working tree, but not the index, the stash or HEAD. That is a written-up incident, not a hypothetical.

The principle that transfers: a rule you merely discourage is not a rule. If something must never happen, it has to be impossible, not just unlikely.
